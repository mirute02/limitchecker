# 決定事項（設計書からの変更点）

[docs/design.md](design.md) を基準に、検討の結果変更した点を記録する。
設計書自体は当初の記録として書き換えない。

## D1. 残量が古いときはグレーアウトして「更新できません」と出す

**決定**: statusLine は Claude Code の実行中しか更新されないという制約を、そのまま受け入れる。
値が古ければ薄く、さらに古ければグレーにして、取得できていないことを明示する。

**理由**: 定期的に残量を取得する手段が存在しないため。`claude` CLI に usage 相当の
サブコマンドはなく（確認済み）、定期取得するにはアプリ側が資格情報を持つ必要がある。
正確さのために資格情報を抱えるより、取れないときに正直にそう表示するほうが、
公開リポジトリとして筋が良い。

**波及**: アプリが独自にアカウントへログインする案を破棄。
アプリが保持する秘密は hub のトークン1つのままになる。

## D2. 公式アプリからは取得しない（不可能）

**決定**: Claude / ChatGPT の公式 Android アプリからは残量を取らない。

**理由**: Android のアプリサンドボックスにより、非 root 端末では他アプリのデータ領域を
読めない（実機で `/data/data/` が Permission denied、root なしを確認）。
アクセシビリティサービスで画面を読む手段は技術的には残るが、全画面の内容を読む権限を
要求するため、本リポジトリのセキュリティ方針と衝突する。

## D3. Android 側に CLI を必要としない

**決定**: Android アプリは hub へ HTTP で問い合わせるだけとし、
Claude Code CLI も Termux も前提にしない。

**理由**: 表示端末に開発環境を要求しないため。CLI が動くのは、もともと作業している
Mac / Linux のみ。Termux は APK のビルドにのみ使う。

## D4. FCM を使わず、常設通知の前景サービスがロングポーリングする

**決定**: 設計書の段階4（FCM）を置き換える。通知領域に常設する通知を出し、
その前景サービスが hub をロングポーリングして即時性を確保する。

**理由**: 常設通知には前景サービスが必要で、常駐しているなら FCM は要らない。
FCM は停止中のアプリを起こすための仕組みであるため。
Firebase プロジェクト、`google-services.json`、トークン管理がまるごと不要になる。

**波及**: ステータスバー（時計・電池の行）には、実行時生成したアイコンで
最も逼迫しているリングの残量を数字で出す。
ただし小アイコンは OS がモノクロに塗るため、色分けはシェードを開いた先で見せる。

## D5. 作業ディレクトリはフルパスを送らない

**決定**: イベントに乗せる作業ディレクトリは basename のみ。送らない設定も用意し、
フルパスを送る選択肢は実装しない。

**理由**: フルパスはユーザ名・顧客名・案件名を含む。[security.md](security.md) 参照。

## D6. アカウントの同定はユーザが宣言したラベルで行う

**決定**: メールアドレスや組織 ID ではなく `LIMITCHECKER_CLAUDE_ACCOUNT` 等のラベルで
マシンを突き合わせ、同一アカウントの残量を1組に畳む。

**理由**: 個人情報を送らずに済み、仕事用と個人用の併用も表現できる。

**注意**: 同一アカウントの値は**合算しない**。枠は共有なので各マシンは同じ値を報告する。
取得時刻が最も新しいものを採用する。

## D7. リングは2周にする

**決定**: 設計書の三重ドーナツを二重にする。外側が5時間枠、中央が週次枠。

**理由**: statusLine の `rate_limits` は `five_hour` と `seven_day` の2つのみで、
内側リングに想定していたモデル別週次枠が存在しない（[findings-statusline.md](findings-statusline.md)）。
週次枠そのものは全モデル合算で取得できるため、残量把握という目的は2周で達成できる。

実在しないデータのために「今日の消費量」や「コンテキスト残量」を内側に充てる案は見送る。
前者は残量ではなくリングの意味が混ざり、後者はセッション単位の値でアカウント単位の
外側・中央と層が食い違うため。

## D8. ドーナツ中心にはリセット時刻を置く。常に5時間枠

**決定**: 中心に「5時間枠の残%」と「5時間枠のリセットまでの残り時間」を置く。
逼迫している枠に応じて切り替えることはしない。

**理由**: 中心の意味が固定されるので読み違えない。
「今から長い作業を始めてよいか」に直結するのは5時間枠のほうであり、
これは本ツールが解決したい困りごとそのもの。

週次枠が逼迫した場合は中央リングの色（50%超=緑 / 20〜50%=黄 / 20%未満=赤）で気づける。
中心を切り替えなくても取りこぼさない。

**波及**: 設計書は「リセットまでの残り時間はリングの下に小さく添える」としていたが、
中心に移すことでリングの下が空き、マシンチップを置く余地ができる。
API 仕様の変更は不要（`resets_at` は既に各リングに含まれる）。

## D9. 即時通知の方式は段階4まで決めない（D4 の修正）

**決定**: D4 で「FCM をやめてロングポーリング」としたが、電池の観点から保留に戻す。
段階2までは **WorkManager 15分 + ウィジェットのタップ更新のみ**とし、
即時通知の方式（ロングポーリング / FCM）は段階4で実測して決める。

**理由**: D4 は実装の簡単さを優先していて、電池では不利だった。
通信は転送量より**回数**が効く。無線は通信のたびに起き、終わっても数秒〜十数秒は
高電力状態が続く。FCM の本来の利点は、端末が既に維持している共通接続に相乗りし、
アプリ固有の接続を増やさない点にある。ロングポーリングはタイムアウトを長くすれば
回数を減らせるが、自前の接続を保つ分だけ不利。加えて Tailscale の常時 ON が要るため、
WireGuard のキープアライブも乗る。

設計書のとおり段階2で毎日使える状態になる。一番電池を食う部分を最後に回し、
「気づけなくて困る」頻度を体感してから選ぶほうが、今決め打ちするより確実。

## D10. 省電力の作りと権限方針

**決定**: 以下を実装上の前提とする。

省電力:
- WorkManager に `NetworkType.CONNECTED` 制約を付け、圏外で無駄打ちしない
- 失敗時は指数バックオフ
- 前回と差分がなければ再描画しない（Bitmap 生成ごと省く）
- 画面 OFF 中はウィジェット更新をスキップする
- ロングポーリングを採用する場合もタイムアウトは長め（5分程度）にする

**電池最適化の除外 (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) は要求しない。**
Doze 中の通知は遅れることを受け入れる。

権限:

| 権限 | 用途 | 実行時確認 |
| --- | --- | --- |
| `INTERNET` | hub への通信 | なし |
| `ACCESS_NETWORK_STATE` | 圏外判定（省電力） | なし |
| `POST_NOTIFICATIONS` | 通知（Android 13+、段階3以降） | あり |
| `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_DATA_SYNC` | 常設通知 | なし |
| `RECEIVE_BOOT_COMPLETED` | 再起動後の復帰（任意） | なし |

実行時ダイアログが出るのは `POST_NOTIFICATIONS` だけ。

**段階2 の実測（ビルド済み APK を `aapt2 dump badging` で確認）**:

```
INTERNET
ACCESS_NETWORK_STATE
WAKE_LOCK
RECEIVE_BOOT_COMPLETED
FOREGROUND_SERVICE
com.limitchecker.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION
```

後半4つは **WorkManager（androidx.work）がマニフェストのマージで自動追加**する。
アプリ側のマニフェストには書いていない。いずれも通常権限で実行時ダイアログは出ないが、
「段階2 は2つだけ」という当初の記述は誤りだったため訂正する。

`FOREGROUND_SERVICE` と `RECEIVE_BOOT_COMPLETED` は段階3・4 の常設通知で必要になるため、
結果的に前倒しで入った形になる。最小構成にこだわるなら WorkManager をやめて
AlarmManager に替えれば2つに減らせるが、段階4 で足し直すことになる。

権限を増やす依存を入れるときは、**ビルド後の APK で実測して確認する**。
マニフェストを読むだけでは足りない。

**取らない権限**: 位置情報、ストレージ、カメラ、連絡先、`QUERY_ALL_PACKAGES`、
アクセシビリティ、`SYSTEM_ALERT_WINDOW`、電池最適化の除外。
公開リポジトリでは権限の少なさがそのまま安全性の説明になる。

## D11. 更新間隔は「画面 ON 中は5分、画面 OFF 中は停止」

**決定**:

| 段階 | 残量の更新 |
| --- | --- |
| 段階2 | WorkManager 15分 + ウィジェットのタップで即時 |
| 常設通知あり | 画面 ON 中は5分ごと、**画面 OFF 中は停止** |

間隔は設定で変更できるようにするが、既定は5分とする。

**理由**: 残量の性質上、1分更新は情報として意味がない。5時間枠は5時間で100%
消費する量なので、1分で動くのはせいぜい 0.3%。リングの見た目は変わらない。
一方で通信回数は 5 倍になる。

画面 OFF 中を止められるのが効く。ウィジェットも常設通知も、見ていないときに
更新する意味がない。

**波及**: 常設通知の前景サービスがどのみち常駐するため、そこから数分ごとに
まとめて取得すればよく、**ロングポーリングも FCM も不要になる**。
D9 で段階4まで保留にした判断は、この方式で解消できる見込み。
ただし即時性が本当に要るかは段階4で実測して確かめる。

なお Android の枠組み上の下限は `updatePeriodMillis` が 30分、WorkManager が 15分。
分単位の更新は前景サービス内の自前タイマーでのみ可能。

## D12. 配色は色覚特性を前提に、色の役割を分ける

**決定**: 設計書の「50%超=緑 / 20〜50%=黄 / 20%未満=赤」をやめ、次のように役割を分ける。

| 手がかり | 表すもの |
| --- | --- |
| 色相 | **どのリングか**。外側（5時間枠）=青、中央（週次枠）=オレンジ |
| 弧の長さ | **残量の多寡**。色に頼らない |
| 朱色 + 線を太く | **逼迫（20%未満）のみ** |

**理由**: 赤と緑で状態を表すのは、最も多い型の色覚特性（P型・D型）で区別できなくなる。
設計書の配色は緑→黄→赤の遷移そのものが情報だったため、この点で成立していなかった。

青とオレンジは P型・D型・T型のいずれでも判別できる組み合わせ（Okabe-Ito の推奨対）。
値は Okabe-Ito のバリアフリー配色から採り、暗い背景では同じ色相を明るくして
コントラストを確保する。

逼迫時は色を変えるだけでなく**線を太くする**。色以外の手がかりを重ねることで、
色が判別できない場合でも気づけるようにする。

残量そのものは弧の長さで表しているため、色が一切読めなくても情報は失われない。

## D13. ドーナツ中心に残量の数字を置かない

**決定**: 中心はリセットまでの残り時間のみにする（D8 の数字表示を取り下げる）。

**理由**: 残量は弧の長さがすでに表している。数字を重ねると中心が混み合ううえ、
同じ情報を2回出すことになる。中心には、弧からは読めない「いつ回復するか」を置くほうが
情報量が増える。

## D14. ウィジェットのサイズに応じて出し分ける

**決定**:

| 幅 | 表示 |
| --- | --- |
| 190dp 未満 | Claude Code のドーナツ1つだけ |
| 190dp 以上 | ドーナツ2つ |

縦に広い場合は、内容を縦中央に寄せる。

**理由**: 従来は常に2つ横並びで、比率だけを拡大縮小していた。
そのため狭いと両方とも読めない大きさになり、縦に広いと下半分が空白になっていた。

あわせて ImageView の `scaleType` を `fitXY` から `fitCenter` に変更した。
報告されるウィジェット寸法と実際の表示領域がずれた場合、`fitXY` では円が楕円に潰れる。

## D15. OS ごとの手順を分けず、スクリプトで吸収する

**決定**: hub の常駐手順を `deploy/install-hub.sh` に集約し、
Linux でも macOS でも**同じコマンドをそのまま使える**ようにする。
アプリ内の OS 切り替えは廃止する。

**理由**: 実際に違うのは常駐の仕組み（systemd と launchd）だけで、
取得・設定・待ち受け先・agent の設定はすべて同じだった。
それなのに手順全体を読み分けさせるのは、実装の都合を利用者に押し付けていた。
違う部分こそ自動化すべきで、手順書を分けるのは筋が悪い。

**実装上の注意**:
- `uname -s` は Termux でも Linux を返す。`systemctl` の有無で見分け、
  Termux では Termux:Boot を案内する
- `sed -i` は GNU と BSD で書式が異なるため使わない
- `realpath` は macOS に無いため使わない
- `python3` は `command -v` で実体を引く。pyenv や Homebrew でも正しい場所を指す
- ユニットと plist は雛形（`.in`）に置換して生成する。
  リポジトリの場所を決め打ちしない

## D16. 常設通知に前景サービスを使わない

**決定**: 通知センターへの常設は `setOngoing(true)` の通常通知で行い、
前景サービスを立てない。更新はウィジェットと同じ `RefreshWorker` から行う。

**理由**: Android 15 以降、`dataSync` 型の前景サービスは24時間あたり6時間までに
制限される。常設表示という用途には使えない。
一方、常設通知そのものは前景サービスなしで出せる。

**効果**:
- 追加の常駐プロセスを持たない（電池とメモリの増加がない）
- `FOREGROUND_SERVICE_DATA_SYNC` の型宣言が不要
- 更新経路がウィジェットと1本化され、取得も1回で済む
- D4 で検討したロングポーリングも不要

**代償**: 更新間隔は WorkManager の15分に揃う。分単位の即時性は出ない。
残量は1分で目に見えるほど動かないため（D11）、この用途では問題にならない。
入力待ちの即時通知は別物で、段階4 で改めて検討する。

**ステータスバーの表示**: 時計や電池が並ぶ行に置けるのは小アイコン1つだけで、
任意の文字は置けない。残量の数字を描いたアイコンを実行時に生成する。
OS が小アイコンをアルファ値だけ使って単色で塗るため、**色は使えない**。
形（数字）だけが残る。色分けは通知を開いた先で見せる。

## D17. ウィジェットは 1×1 まで縮められるようにする

**決定**: `minWidth` / `minHeight` を 57dp（1セル相当）まで下げ、
既定の配置は 2×1 にする。幅に応じて内容を3段階で減らす。

| 幅 | 内容 |
| --- | --- |
| 112dp 未満 | ドーナツ1つ。サービス名も補足も出さず、リングと時間のみ |
| 112〜190dp | ドーナツ1つ＋サービス名 |
| 190dp 以上 | ドーナツ2つ＋サービス名 |

**理由**: 小さく置きたいという要望に対し、縮小だけで対応すると文字が読めなくなる。
入る情報量に合わせて要素を落とすほうが、小さくても用を成す。
省略形では余白も詰めてリングを大きく取る。

## D18. 通知の見せ方を3段階に分ける

**決定**: 使える表現領域に応じて、出す情報を変える。

| 場所 | 出すもの | 制約 |
| --- | --- | --- |
| ステータスバー | ドーナツの**形** | 小アイコン1つのみ。OS が単色に塗る |
| 通知（折りたたみ） | リングの絵 + 残量の数字 + 回復までの時間 | 横長の狭い領域 |
| 通知（展開） | ウィジェットと同じ絵を大きく | 自由 |

**ステータスバーで形を使える理由**: OS は小アイコンを単色で塗るが、
**アルファ値は保持される**。薄いトラック（alpha 70）の上に濃い弧（alpha 255）を
重ねると、単色のままでもドーナツとして読める。電池アイコンと同じ読み方になる。

数字をやめて形にしたのは、24dp では2桁が潰れるため。
正確な値は通知を開けば出る。取得できないときだけ "?" を出す。

**折りたたみ時**は `setLargeIcon` にリングの絵を入れる。
数字だけより状態が伝わり、ウィジェットと同じ色使いなので見た目が揃う。

**展開時**は `BigPictureStyle` でウィジェットと同じ描画を大きく出す。
描画コードを共有しているので、見た目のずれが生じない。

アクセント色（`setColor`）は外側リングと同じ判定にし、
逼迫時は朱色にして通知欄でも気づけるようにする。

## D19. ステータスバーの表示内容を選べるようにする

**決定**: 何を出すかを利用者が選ぶ。既定は2本のリング。

| 選択肢 | 表示 |
| --- | --- |
| ドーナツ（5時間＋週次） | リング2本 |
| ドーナツ（5時間のみ） | リング1本。太く描けるので形が読みやすい |
| ドーナツ（週次のみ） | リング1本 |
| 数字（5時間の残量） | `65` |
| 数字（週次の残量） | `70` |
| 数字（5時間の回復まで） | `1h` / `45m` / `4d` |

**理由**: 何を重視するかは人と状況で変わる。形は大づかみに速く読め、
数字は正確に読める。どちらが良いかを一律に決める理由がない。

**制約**: 置けるのは小アイコン1つで 24dp しかないため、
**どのモードでも出す情報は1種類に絞る**。詳しい値は通知を引き下ろせば見える。
数字は3桁で潰れるので 100% は 99 に丸め、時間表記も3文字までにする。
文字数に応じて字の大きさを変える。

## D20. ウィジェットの背景を選べるようにする

**決定**: 不透明・半透明・透過の3段階。既定は不透明。

**理由**: 透過は壁紙に馴染むが、壁紙の色によっては文字が沈んで読めなくなる。
一律に透過にはできないため選択制にする。

**透過時の可読性**: 文字と数字に影を落とす。暗いテーマなら黒、明るいテーマなら白の
影を置くことで、反対色の壁紙の上でも輪郭が残る。

## D21. 手順のコマンドは1つずつコピーできるようにする

**決定**: 連続するコマンドをまとめず、**1コマンド＝1ブロック＝1ボタン**にする。
コマンドとボタンを同じ行に並べ、対応関係を見て分かるようにする。

**理由**: まとめてコピーできるほうが手数が少ないと考えたが、
どのボタンが何をコピーするのかが分かりにくかった。
手数より、押す前に何が起きるか分かることを優先する。

## D22. 手順は文字列リソースに置かず、型付きのデータで持つ

**決定**: hub の準備手順を `SetupSteps.kt` に `Head` / `Body` / `Command` の
並びとして持つ。文字列リソースと、行頭記号による解析をやめる。

**理由**: 同じ場所で2回壊した。

1. XML 中の生の改行が空白に畳まれ、手順が一続きの文章になった
2. `<リポジトリ>` がタグとして解釈され、ビルドが失敗した
3. 修正後、エスケープが失われて再び改行が潰れ、**行頭記号の判定が一度も成立せず、
   コピーボタンが1つも生成されない状態になっていた**。
   画面には文章が出ていたため、壊れていることに気づきにくかった

エスケープの正しさに依存する設計そのものが原因だった。
Kotlin の文字列は改行も `<` も素通しで、解析も不要になる。
コマンドに個別のコピーボタンが付くことが、型として保証される。

**教訓**: 表示されていることは、正しく構造化されていることを意味しない。
本数や件数を数えて確かめる。`SetupSteps.commandCount` はそのために置いている。

## D23. 2つの枠を小アイコンで出すときは、同心円ではなく上下に分ける

**決定**: ステータスバーで5時間枠と週次枠の両方を出す場合、
同心円2本をやめ、**円を上下に分けて半周ずつ**で表す。
上半分が5時間枠、下半分が週次枠。どちらも左端から伸び、
両方満タンなら1つの円になる。左右の端に12度の隙間を空けて境目を示す。

**理由**: 同心円2本は 24dp では潰れて1本に見える。
実装にも `middleRadius > stroke` という条件が入っており、96px で計算すると
成立せず**内側が一度も描かれていなかった**。条件で描画が消える作りだったため、
不具合として表に出るまで気づけなかった。

上下に分ければ、それぞれが半径いっぱいの太さを使える。
値の範囲は半周（168度）に圧縮されるが、小さいアイコンで求められるのは
「だいたいどれくらい残っているか」なので、その粒度で足りる。
正確な値は通知を引き下ろせば見える。

**教訓**: 描画を条件で飛ばすと、消えたことに気づけない。
描くか描かないかではなく、常に描いて形を変えるほうが安全。

## D24. コピーは図形で示す

**理由**: コマンドと同じ行に文字のボタンを置くと幅を食い、
長いコマンドが折り返して読みにくくなる。
標準アイコンは端末やバージョンで有無が変わるため、自前で描いて確実にする。
文字色と同じ色で描くので、明暗どちらのテーマでも馴染む。

## D28. Codex は app-server の API から取得する（訂正あり）

**当初の結論は誤っていた。** 「認証情報を読まずに残量を取る経路は存在しない」と
書いたが、これは CLI のサブコマンド・`doctor`・`exec --json` のイベントしか
調べていなかったための誤りだった。**app-server のプロトコルを見ていなかった。**

### 正しい状況

Codex App Server の JSON-RPC に `account/rateLimits/read` がある。
`codex app-server generate-json-schema` でプロトコルを出力して確認した。

```
account/rateLimits/read
account/rateLimits/updated
account/usage/read
account/rateLimitResetCredit/consume
```

応答の型は `GetAccountRateLimitsResponse.json` に定義があり、
`usedPercent` / `windowDurationMins` / `resetsAt` / `PlanType` / `CreditsSnapshot`
を含む。5時間枠と週次枠は `windowDurationMins` で区別する（300 と 10080）。

**呼び出し側は `~/.codex/auth.json` を読まない。** app-server がログイン済みの
認証を自分で扱い、クライアントは JSON-RPC を投げるだけでよい。
したがって [security.md](security.md) の不変条件に反しない。

### 消費について

`initialize` と `account/rateLimits/read` だけなら、`thread/start` も `turn/start` も
行わないためモデルへの推論要求にはならず、5時間枠・週次枠を消費しない。
実装では取得間隔を絞るが、これは枠の消費ではなく通信回数を抑えるため。

### 呼び方

```
{"method":"initialize","id":1,"params":{"clientInfo":{...}}}
{"method":"initialized","params":{}}
{"method":"account/rateLimits/read","id":2}
```

標準入力を閉じると応答前にサーバが終了するため、応答を受け取るまで開いておく。

### 実機での動作確認

**Android (Termux) を含め、動作する。**

```
5h 100%
7d 14%
```

一度は取得に失敗し `error sending request for url (.../wham/usage)` が出たが、
これはプロトコルの問題ではなく**起動する実行ファイルを間違えていた**ため。

Termux では Codex の通信に回避策（proot で `/etc/resolv.conf` を差し替え、
`SSL_CERT_FILE` を指定）が要る場合があり、その環境ではラッパースクリプトを
用意して `alias` で使うのが一般的。**しかし alias はスクリプト内では展開されない。**
`codex app-server` と書くと回避策を通らず生のバイナリが起動し、通信だけが失敗する。

そのため `CODEX_BIN` で実行ファイルを指定できるようにしてある。

```
LIMITCHECKER_CODEX_BIN=/path/to/codex-wrapper
```

**この症状の見分け方**: `error sending request for url` は HTTP 401/403 ではなく、
HTTP クライアント自体が通信に失敗したときの形。認証の問題ではないので、
`auth.json` を読む方式に切り替える理由にはならない。
同じ URL に `curl` が届く（401 が返る）なら、経路の問題ではなく起動方法を疑う。

### 教訓

**「CLI に見当たらない」を「経路が存在しない」と書いた。** 調べた範囲と
結論の範囲が食い違っていた。`generate-json-schema` のような、
プロトコルそのものを吐く手段があるなら先にそれを見るべきだった。

**通信の失敗を、方式の限界と読み違えかけた。** 取得できないことを根拠に
「保留」と決めたが、実際は起動する実行ファイルが違っただけだった。
エラーの形（`error sending request` は通信層、401/403 は認証層）を
読み分けていれば、もっと早く切り分けられた。

## D28b. 未設定のサービスは表示しない

**決定**: 一度も報告がないサービスは、ウィジェットに表示しない。

**理由**: 設定していないだけのものを「取得不可」とグレーで出し続けると
故障しているように見える。hub は `configured` を返し、未設定（一度も報告なし）と
設定済みだが取得に失敗した状態（`available: false`）を区別する。
後者は従来どおりグレーで表示する。

Codex 対応が入っても、設定していない人には Claude だけが出るため、この分離は有効。

## D29. 設定項目を減らす

**決定**: 14通り → 10通りに整理した。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 配色 | 5種 | **3種**（青とオレンジ / 濃淡のみ / 信号） |
| ステータスバー | 6種 | **4種**（両方 / 5時間リング / 5時間の数字 / 回復まで） |
| 背景 | 3種 | 3種（変更なし） |

**理由**: 競合を調べたところ、設定がほぼ無いことを売りにしているものが複数あった
（Windows のトレイアプリは "zero configuration" を明記）。
削ったのは役割が重複していたもの。「青と青緑」「青と赤紫」は「青とオレンジ」と
同じ役割で、判別しやすさだけが劣る。週次枠だけを出すモードは、
5時間枠のほうが判断に直結するため使う場面が想定しにくい。

選択肢は少ないほうが、どれを選べばよいか迷わない。

## D30. 面積に応じて表現を変える

**決定**: ウィジェットの大きさで表現そのものを切り替える。

| 大きさ | 表現 |
| --- | --- |
| 幅 220dp 以上 **かつ** 高さ 170dp 以上 | **横棒**。サービス名・枠の種類・残量・回復までの時間を並べる |
| 幅 190dp 以上 | ドーナツ2つを横並び |
| 縦が幅の 1.6 倍以上 | ドーナツ2つを縦積み |
| それ以外 | ドーナツ1つ |

**理由**: ドーナツは「だいたいどれくらい残っているか」を速く伝えるのに向くが、
面積が増えても伝わる情報量が増えない。大きく置いたのに余白ばかりになる。

横棒なら、同じ面積に**何の枠かという説明**を添えられる。
ドーナツでは外側と内側の対応を覚える必要があったが、横棒なら書いてある。

## D31. 縦積みの余白を詰める

**決定**: 縦に積むとき、各ドーナツを自分の半分の領域の中央に置くのをやめ、
2つをひとまとまりとして配置する。余白も 6% から 3% に詰めた。

**理由**: 半分ずつに分けて各々を中央寄せすると、上下に使われない隙間が4か所できる。
1×2 のような小さいウィジェットでは、その隙間が面積の大半を占めてしまう。

## D32. 逼迫色を深紅に変える

**決定**: 逼迫時の色を `#D55E00`（朱色）から `#B3002D`（深紅）に変更する。

**理由**: 実測したところ、朱色と中央リングのオレンジ `#D68A00` の距離が **44 しかなかった**。
他の組み合わせは 279 ある。**中央リングが逼迫しても、色が変わったと分からない状態**だった。

深紅は青ともオレンジとも 149 の距離があり、D型（緑が見えにくい型）で近似しても
120 を保つ。色覚特性の方針（D12）を崩さずに、逼迫を判別できる。

| 組み合わせ | 変更前 | 変更後 |
| --- | --- | --- |
| オレンジ ↔ 逼迫色 | 44 | **149** |
| D型でのオレンジ ↔ 逼迫色 | 35 | **120** |

## D33. ステータスバーと通知に出すサービスを選べるようにする

**決定**: Claude Code / Codex / 両方 から選ぶ。既定は Claude Code。

ウィジェットは幅があるので常に両方出すが、ステータスバーは小アイコン1つ、
通知の折りたたみ時も1行しかないため、出すものを選ぶ必要がある。

「両方」を選ぶと、ステータスバーは円の左半分が Claude Code の5時間枠、
右半分が Codex の5時間枠になる。1サービスを選んだ場合は、
従来どおり左が5時間枠・右が週次枠。

## D34. 4値をステータスバーに出すときは縦棒にする

**決定**: サービス「両方」かつ「グラフ（5時間と週次の両方）」を選んだ場合、
ステータスバーは**4本の縦棒**にする。左2本が Claude Code、右2本が Codex で、
それぞれ5時間枠と週次枠。2本ずつ間隔を空けてサービスを区切る。

**理由**: 24dp に4つの値を入れる必要がある。同心円を2本重ねて各々を左右に分ければ
論理的には収まるが、その大きさでは潰れて読めない（D23 で同じ失敗をしている）。

**この大きさでは、角度より高さのほうが正確に読める。** 電波強度計が縦棒なのも同じ理由。
薄い枠の上に濃い棒を重ねることで、OS が単色に塗っても「満タンに対してどれだけ」が残る。

枠は値が無いときも描く。描かないと「空」と「未取得」の区別がつかない。

1サービスだけを選んでいる場合は、従来どおり円を左右に分ける（値が2つなので潰れない）。

## D35. 余りは「名前」か「等間隔」で埋める

**決定**: 縦積みでドーナツの大きさが幅で決まり縦が余る場合、余りをこう扱う。

| 余りの大きさ | 扱い |
| --- | --- |
| 名前が 9dp 以上で描けるなら | **サービス名に充てる**。情報が増える |
| それ未満 | **上・間・下を同じ間隔にする** |

**理由**: 余りを上下に寄せると、片寄った空きができて事故のように見える。
等間隔なら意図した配置に見える。

名前に 9dp の下限を設けたのは、それ未満だと読めないため。
検算したところ 1×2 では 5.1dp にしかならず、描いても意味がなかった。
**読めない文字を描くくらいなら、配置で埋めるほうがよい。**

| サイズ | 径 | 間隔 | 名前 |
| --- | --- | --- | --- |
| 1×1 | 26dp | 1.5dp | なし |
| 1×2 | 52dp | 8.4dp | なし |
| 1×3 | 52dp | 20.2dp | あり（11.5dp） |

## D36. アプリの英語化は後回し。ただし積み上げない

**決定**: アプリ UI の英語化は、機能が落ち着いてから行う。
ただし**今後追加する利用者向けの文字列は `strings.xml` に入れる**。

**理由**: UI がまだ動いている。1日のうちに選択肢のラベルを複数回変えており
（配色5種→3種、リングの説明を2回）、翻訳を先に作ると変更のたびに
2か所を直すことになり、必ず片方が古くなる。

### 着手前に知っておくべきこと

**`strings.xml` に `values-en` を足すだけでは終わらない。**
実測したところ、Kotlin に約40か所の日本語が直書きされている。

| ファイル | 箇所 | 残るもの | 直書きの理由 |
| --- | --- | --- | --- |
| `SetupSteps.kt` | 22 | hub の準備手順まるごと | XML のエスケープで3回壊したため型付きデータにした（D22） |
| `DonutRenderer.kt` | 9 | ウィジェット内の文字 | `Context` を持たない純粋な描画器にしているため |
| `HubClient.kt` | 6 | エラーメッセージ | **設計上の不備**。通信層が UI の文言を所有している |
| `StatusNotification.kt` | 2 | 時間の単位 | 同上 |

### 着手時にやること

1. **`HubClient` は理由コードを返すよう直す。** これは翻訳と関係なく直す価値がある。
   通信層が表示文言を持つべきではない
2. `DonutRenderer` にはラベルの組を渡す。`Context` を持たせない設計は維持する
3. `SetupSteps` は見出しと本文だけリソース ID に戻す。
   **コマンドは直書きのまま残す**（翻訳対象ではないうえ、`<` を含むため）
